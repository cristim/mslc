# The MSL corpus, taken from indium's test suite. Each .metal file is paired
# with a .metallib that Iridium already translates to GPU-verified SPIR-V, so
# mslc's output has a reference to be compared against.
#
# A second group is the subset of Metal that Blender 4.5.14's
# gpu/metal/mtl_context.mm actually calls through newLibraryWithSource:, frozen
# here verbatim so mslc's progress on real shaders is measured too.
#
# Every entry says what is expected of it, and that is what the corpus test
# asserts:
#
#   expect=valid              the file has to compile to spirv-val-valid SPIR-V.
#                             Not merely to return success: compiling to
#                             something spirv-val rejects fails here too.
#
#   expect=unsupported:WHAT   the file has to fail, and its diagnostic has to
#                             mention WHAT, which is the construct currently in
#                             the way. A file blocked on the preprocessor says so:
#                             its attributes are named by enumerants a shared
#                             header declares, its types are typedefs and
#                             simd's vector_uint2, and reading a header and
#                             expanding its macros is a larger piece than the rest
#                             of this list together. This is what keeps the list honest in
#                             both directions: a supported fixture cannot stop
#                             compiling unnoticed, and an unsupported one cannot
#                             quietly change what it is blocked on. When a
#                             construct is implemented, the entry that names it
#                             fails until it is edited here to expect=valid,
#                             which is the only way the count moves.
#
#   expect=invalid:WHAT       the file has to compile, and spirv-val has to
#                             reject the module with a diagnostic mentioning
#                             WHAT. This is the third thing between the two above:
#                             mslc understands the source and emits a module, but
#                             Vulkan's own rules refuse that module, so it is
#                             neither a fixture mslc supports nor one it refuses.
#                             The entry is asserted by name in the same way, so a
#                             fix that makes the module valid is as visible as a
#                             regression that changes the reason it is rejected.
#
#                             texturing is the second thing this is for, and it
#                             is a representation rather than a number. Its
#                             vertices are packed, so the host writes them 40
#                             bytes apart (indium's own test asserts it:
#                             static_assert(sizeof(Vertex) == 40)), and a runtime
#                             array of a struct that holds a v4float is one whose
#                             stride Vulkan's relaxed block layout will only
#                             accept as a multiple of 16. Metal's 40 is right and
#                             the multiple of 16 is wrong, so neither number can
#                             be emitted. Iridium translates the same source by
#                             giving a packed vector a different type: a
#                             packed_float4 member is float[4] with ArrayStride 4
#                             rather than a v4float, which is a scalar array and
#                             so has no register to align to. That is a change
#                             to how a packed member is typed and read, not a
#                             layout number, so it is a separate piece of work.
#

# to be below M, and that is not a failure of the test.
